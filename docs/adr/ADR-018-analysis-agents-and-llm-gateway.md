# ADR-018: Analysis agents 5-8, versioned risk rubric, full assurance and the bounded LLM gateway (M7)

**Status:** Accepted (M7). Amended by [ADR-021](ADR-021-agent-validation-pass.md): a model may also review agent outcomes, with one-way effects only.

## Decision
1. **Deterministic first; a model only explains.** Agents 5 (risk and correlation), 6 (architecture and modernization) and 7 (independent assurance) are deterministic handlers. The optional model (ADR-009) can only write a *candidate narrative* for a scenario or a recommendation. It never scores, selects, approves or changes anything, has no tool interface at all (`ModelClient.complete` takes text and a JSON schema, nothing else), and is off unless `ai_enabled` **and** a model id **and** its reviewed weights licence are configured. A run uses AI only if the launch request says `ai_assist: true` *and* the platform has AI enabled (otherwise 422 `AI_NOT_ENABLED`). The endpoint must be loopback; the client never follows redirects, ignores proxies, caps the response at 256 KB and refuses any reply carrying `tool_calls`. No weights are downloaded or bundled by this repository.
2. **Versioned risk rubric (`risk-rubric-1.0.0`).** score = severity + owner criticality + exposure, with fixed thresholds (P0 >= 8, P1 >= 6, P2 >= 4, else P3). A business-risk tier exists **only when every input is known**: criticality comes from the owner/inventory and only the rubric's own labels count (free text such as "tier-1" is *unknown*, never guessed); unverified exposure scores 0 and is listed as missing evidence. Otherwise the tier is `null`, basis `NEEDS_POLICY_REVIEW`, with a separate, labelled severity-only `provisional_tier`. A database CHECK makes "tier present exactly when basis is COMPLETE" unrepresentable to violate. The rubric thresholds and the sample architecture catalog are **placeholders to be approved by the policy owner**.
3. **Agent 5** builds scenarios only from findings already recorded: two or more weaknesses on the same asset, every link OBSERVED and citing its finding and evidence reference. Nothing is inferred (INFERRED links are supported by the contract but never produced; Agent 7 would send one to review). A scenario is complete only if every constituent risk is complete.
4. **Agent 6** maps findings to a sample catalog of approved target patterns and drafts recommendations: each cites its findings, effort is **unknown** (never estimated), missing owner/criticality become explicit owner questions, there is a rollback, an acceptance test and validation steps, and text is scanned to forbid executable commands, compliance/certification claims and lifecycle (EOL/EOS) claims. A recommendation records a human decision (`ACCEPT` -> `APPROVED_FOR_PLANNING`, `DEFER`, `REJECT`) with a mandatory redacted reason; **no code path executes a recommendation**, and the database refuses acceptance without decider, reason and an ACCEPT assurance verdict.
5. **Agent 7 validates everything built on findings.** It recomputes each risk from stored factors with the pinned rubric, and checks scenarios (constituent verdicts, asset and chain consistency, tier recomputation, duplicates, text safety), recommendations (catalog pattern applies, rollback/test present, no effort estimate, assets and tier consistent, text safety) and narratives (re-runs the grounding validator on the *stored* output, requires an ACCEPTed parent, sends injection-flagged input to review). A parent is ACCEPT only if all its constituents are ACCEPT. **Only ACCEPT items reach the report**; the rest are counted and disclosed as limitations (auditors can list rejected candidates).
6. **Grounding validator.** Every CVE, control id, IP address, URL, port and risk tier in model output must already appear in the facts that were sent; claims must cite finding and asset ids that exist in the subject; hidden/control characters, commands, compliance claims and lifecycle claims are rejected; unknown JSON fields (e.g. `tool_calls`) are a schema failure. A grounding failure is **not retried**; malformed output and transport failure get one retry, then `UNAVAILABLE`.
7. **Prompt-injection posture.** The model receives only a whitelisted projection of validated findings (title, category, severity, asset ids, evidence refs, control ids, plus deterministic text), never raw evidence or observed values, JSON-escaped under a "DATA, untrusted" frame, redacted first. Injection-looking strings are flagged on the call record and push the narrative to review. The grounding validator, not the prompt, is the control.
8. **Orchestration.** New states CORRELATION and ARCHITECTURE_ANALYSIS sit between policy evaluation and assurance. Model calls happen **outside the run-row lock and any transaction**; narratives and the append-only `llm_calls` provenance row (model, prompt version, input/output hash, attempts, defects) are written once, idempotently. With AI off, unavailable, rejected or timing out, the deterministic report is identical (asserted).
9. **Ticket drafts** go to an outbox that can only hold `DRAFT` rows and are created only for accepted recommendations, by approvers, when `enable_itsm_ticket_creation` is on (default off). Nothing is ever delivered.

## Known limitations
- The rubric weights, thresholds and the architecture catalog are samples; they are labelled as such in the UI and report and need policy-owner approval before use.
- ~~Exposure is category-derived; real reachability analysis does not exist~~ **Resolved (ADR-041):** host-firewall rules and declared-vantage scans raise exposure, backed by stored edges; host findings with no such evidence still score exposure 0 and are flagged.
- Scenarios are same-asset groupings only; there is no attack-path or graph reasoning (ADR-010 stays planned).
- The grounding validator is pattern-based: numbers of things ("12 hosts"), product names and prose claims that carry no identifier are not checked. Unusual control-id formats can cause false rejections (safe direction).
- The model was exercised **only with scripted stubs and a local fake runtime**; behaviour of any real model, its latency and its output quality are unverified. No weights were downloaded.
- Deciding on a recommendation has no separation-of-duties rule beyond the approver role.
